# 研究与设计决策

## 1. 使用方式

本文记录产品决策的依据，不构成医学建议。研究结论用于解释为什么提供可调节的工作/休息结构和活动提示，不能被产品文案改写成“保证健康”“治疗久坐”或“最科学唯一方案”。

调研日期：2026-09-07。

## 2. 已锁定决策

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 默认周期 | `30/5/30/5/30/10` | 用户指定的起始偏好；所有时间可调。 |
| 默认检测 | 系统输入闲置，40 秒阈值 | 无须摄像头权限，能在用户使用其他应用时检测系统级闲置。 |
| 摄像头 | Phase 2 可选、本地人脸在场 | 降低隐私与实现风险；不做身份识别或严格反欺骗活检。 |
| 休息模式 | 活动休息 + 桌前休息 | 区分“离席”与“暂不输入”的不同习惯。 |
| 站立专注 | Phase 3 手动选择、专注时长减半 | 不从摄像头推断真实姿势，避免静态久站等同运动的错误承诺。 |
| 统计 | 仅完成专注分钟 | 自动暂停、跳过和未完成轮不应被计入完成量。 |
| 数据 | 完全本地离线 | 不需要账号、云同步或遥测即可完成核心体验。 |

## 3. 番茄钟与默认时长

### 3.1 证据结论

传统番茄钟通常采用 25 分钟专注、5 分钟短休、若干轮后长休，但“25 分钟”不是唯一经科学验证的最优时长。

2025 年的范围综述收录的少量随机对照试验使用了 `24/6` 和 `12/3` 的结构化间歇，并报告相对自定休息更低的疲劳和更好的自评专注等结果。该结论支持“有计划的工作-休息结构”值得提供，但研究情境主要与学习有关，样本量和外推范围有限，不能推出任何人都应使用固定 25 分钟或 30 分钟。

来源：[Assessing the efficacy of the Pomodoro technique in enhancing anatomy lesson retention during study sessions: a scoping review](https://pmc.ncbi.nlm.nih.gov/articles/PMC12532815/)

### 3.2 产品决策

- `30/5/30/5/30/10` 只作为用户选择的默认节奏，不标注为医学最优或普适最佳。
- 每个时长及每周期专注轮数可在设置中调整。
- UI 文案使用“默认节奏”“可按工作方式调整”，不使用“科学强制”“保证效率”等断言。
- 因为复杂任务可能需要更长的上下文建立时间，用户可把专注时长调整到 5-120 分钟。

## 4. 休息、久坐与站立

### 4.1 活动间歇

CDC 的工作场所活动间歇指南建议将短时活动间歇纳入工作日，并举例说明 5-10 分钟的活动休息可以在办公室完成。CDC 同时强调成年人每周需要至少 150 分钟中等强度活动，且应“多动、少坐”。该指南支持应用提供短休和离席提示，但不支持把应用的短休计时直接等同于达成每周运动建议。

来源：[CDC - Physical Activity Breaks for the Workplace](https://stacks.cdc.gov/view/cdc/81144)

一项 2025 年面向办公室工作者的系统综述与 Meta 分析指出，电脑提示干预与工作日坐姿时间降低及步数增加相关；纳入研究中的间歇方案从每 30 分钟到每小时一次、每次 1-10 分钟不等。这说明“电脑提醒”是可伸缩的行为支持手段，但并未给出可套用到每个人的单一正确时长。

来源：[The effect of computer prompt in breaks of sedentary behaviour among office workers](https://pmc.ncbi.nlm.nih.gov/articles/PMC12164069/)

### 4.2 站立不是活动的替代品

静态久站本身也可能造成不适。CDC 资料指出，长期静止站立可能关联背部和腿部问题，并建议提供坐、站、走动等姿势变化机会。因此产品不应宣传“只要站着就一定更健康”，也不应要求用户长时间保持站姿。

来源：[The hazards of just standing around](https://stacks.cdc.gov/view/cdc/193830)

### 4.3 产品决策

- 活动休息的判定语义是“离开工位的代理信号”，而非“完成了运动”。
- 桌前休息的目标是暂停输入，不声称用户已进行了身体活动。
- Phase 3 的站立专注为用户手动启动的短专注预设，默认采用普通专注时长的 50%。
- 站立模式文案建议用户根据自身舒适度坐、站、走动和休息；不提供医疗处方或姿势评分。

## 5. 摄像头、权限与隐私

### 5.1 技术事实

`MediaDevices.getUserMedia()` 会请求用户允许使用摄像头，用户拒绝或没有可用设备时会失败，也可能出现用户未作决定而 Promise 长时间不结算的情况。应用必须把摄像头视为可选能力，不能令核心计时依赖成功授权。

来源：[MDN - MediaDevices.getUserMedia()](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

### 5.2 产品决策

- Phase 2 首次开启摄像头前显示清晰说明：只在设备本地处理、不开启上传、不保存视频或脸部特征、可随时关闭。
- Renderer 内请求 `getUserMedia({ video: ... , audio: false })`，不请求麦克风。
- 使用打包的本地 MediaPipe 模型做存在检测；只把布尔 `present/away`、序号和时间戳传给 Main。
- 摄像头被拒绝、设备不可用、流中断或模型失败时，自动回退到输入监测并让用户看到原因。
- 不将“检测到人脸”称为“活体检测通过”。它不能可靠抵抗照片、屏幕视频、光线遮挡或模型误检。

## 6. Electron 安全与系统监测

Electron 的安全指南要求隔离上下文、不要在 Renderer 中启用 Node 集成、限制 IPC 和权限请求。这个项目采用 Main 管理系统能力、preload 暴露窄 API、Renderer 不直接访问 Node/SQLite 的结构。

来源：[Electron Security Tutorial](https://www.electronjs.org/docs/latest/tutorial/security)

Electron `powerMonitor` 提供系统闲置时间与电源事件，是跨平台的输入闲置适配入口。Phase 1 仍必须在真实 macOS 与 Windows 上验证其在小挂件未聚焦、用户使用其他应用、睡眠/恢复等场景的行为；如果平台实现不满足需求，再以等价原生 API 补充。

来源：[Electron powerMonitor API](https://www.electronjs.org/docs/latest/api/power-monitor)

### 6.1 最小数据原则

| 数据 | 是否处理 | 是否持久化 |
| --- | --- | --- |
| 距最近输入的秒数 | 是 | 否 |
| 当前输入在场状态 | 是 | 仅内存快照，不保留历史 |
| 摄像头帧 | Phase 2 内存内短暂处理 | 否 |
| 人脸边界/置信度 | Phase 2 内存内短暂处理 | 否 |
| 人脸嵌入、身份、年龄、情绪 | 否 | 否 |
| 按键内容、鼠标位置 | 否 | 否 |
| 已完成专注轮时长和日期 | 是 | 是，本地 SQLite |

## 7. 参考实现：Pomotroid

本地相邻目录 `/Users/bytedance/code/Easton/pomotroid` 被作为产品和工程参考，不作为本项目源码依赖或复制来源。

调研到的可借鉴点：

- 紧凑小挂件、托盘、通知、统计热力图和主题的桌面交互形态。
- 将“人脸在场”和“系统输入在场”归一为同一个 presence controller，再根据专注/休息反转判定逻辑。
- 本地 MediaPipe 人脸检测、隐藏视频元素和摄像头健康检查的结构。
- 仅用系统级闲置时间，而不是小窗口 DOM 事件，来判断用户是否继续使用计算机。

不可直接采用的点：

- 该项目使用 Tauri、Rust 和 Svelte，本项目使用 Electron、Go 和 React。
- 其已查看实现对非 macOS 的系统闲置时间返回“始终活跃”占位值；本项目首发 Windows，不能保留这个缺口。
- 其人脸检测是“脸是否存在”的实现，不应被扩展为强活体检测或活动量判定。

## 8. 被排除或延期的方案

| 方案 | 处理 | 原因 |
| --- | --- | --- |
| 云端视频/AI 检测 | 排除 | 与完全本地和最小数据原则冲突。 |
| 人脸识别或身份验证 | 排除 | 不解决计时核心问题，增加隐私和安全成本。 |
| 严格照片/视频反欺骗 | 延期且默认不承诺 | 需要专门模型、更多数据与误判评估。 |
| 摄像头姿态/动作识别 | 延期 | 取景、遮挡、设备差异和隐私影响大；离席信号足够支持第一阶段。 |
| 强制全屏休息遮罩 | 排除 | 可能阻断紧急工作；改用通知、状态和用户可控的下一步。 |
| 自动工作日排程 | 排除 | 用户提供的工作时段仅为使用背景，当前产品目标是可配置的计时与休息。 |
| 账号/同步/远程分析 | 排除 | 先验证本地体验，避免扩大数据面。 |

## 9. 后续重新评估条件

以下情况发生时，才重新评估对应决策：

- 用户反馈证明 `30/5/30/5/30/10` 不适合主要任务类型：调整默认值或增加预设，而不是固定强制一种时长。
- Windows 真实设备上 Electron 闲置时间不可靠：实现并测试 Main 层原生适配器。
- 摄像头误暂停率影响使用：先优化本地防抖、回退和透明状态，再考虑更复杂模型。
- 站立模式用户使用率高且有明确需求：开展单独的姿态/活动检测可行性评估，不在未验证前引入。
- 用户需要跨设备同步：单独设计账户、加密、冲突处理与隐私评审，不能把本地 SQLite 直接上传。
